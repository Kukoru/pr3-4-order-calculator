## 1. Какая проверка защищает программу от наиболее вероятной ошибки входных данных и где она расположена

**Проверка:** `OrderCalculator.validateQuantity(int)`.

**Расположение:** класс `OrderCalculator`, метод `validateQuantity`.

**Почему именно она.** Наиболее вероятная ошибка — количество `0` или отрицательное число. `Scanner.nextInt()` спокойно принимает `0` и `-5`, а умножение на такое количество даёт бессмысленный (нулевой или отрицательный) результат, который дальше уйдёт в расчёт НДС и будет выведен как «итоговая стоимость заказа». Это самая опасная ошибка, потому что она **не приводит к падению программы** — она приводит к тихо неверному ответу.

**Как защищает.** Метод сравнивает `quantity` с константами `MIN_QUANTITY = 1` и `MAX_QUANTITY = 10_000` и возвращает текст ошибки. В `Main.run` этот текст печатается в `System.err`, и расчёт **не выполняется**.

## 2. Какой метод или класс содержит ключевое бизнес-правило и почему вы разместили его именно там

**Ключевое бизнес-правило:** «базовая сумма → скидка в процентах → НДС после скидки».

**Метод:** `OrderCalculator.calculateTotal(int, double, double, double)`.

**Почему там.**
1. Это **бизнес-правило**, а не UI. `Main` — только ввод/вывод, `OrderCalculator` — вся математика.
2. Правило задано в одном месте: `calculateBase` → `applyDiscount` → `calculateVat`. Если поменяется порядок («НДС до скидки») — правится одна строка.
3. Тот же метод вызывается и из `SelfCheck`, что позволяет тестировать правило независимо от UI.

**Как размещено:**
```java
public static double calculateTotal(int quantity, double price,
                                    double discountPercent, double vatRate) {
    double base = calculateBase(quantity, price);
    double afterDiscount = applyDiscount(base, discountPercent);
    return calculateVat(afterDiscount, vatRate);
}
```

## 3. Как Activity-диаграмма отражает один конкретный участок вашего кода

**Участок кода** — тело метода `OrderCalculator.calculateTotal`.

**Блок A2 на Activity-диаграмме:**
```
sum = base × (1 − discount/100); total = sum × (1 + VAT_RATE/100)
```

**Соответствие построчно:**

| Activity A2 | Код |
|---|---|
| `base = quantity × price` | `calculateBase(quantity, price)` |
| `sum = base × (1 − discount/100)` | `applyDiscount(base, discountPercent)` |
| `total = sum × (1 + VAT_RATE/100)` | `calculateVat(afterDiscount, vatRate)` |

То есть блок A2 — это буквально тело `calculateTotal`, развёрнутое в три шага.

**Изменение:** ставка НДС (вариант 7 — 40 %).

**Почему.** Ставка вынесена в константу `public static final double VAT_RATE = 40.0`. `Main` и `SelfCheck` не знают конкретного числа — они получают его через `OrderCalculator.VAT_RATE`. Чтобы перейти, например, на 25 % (вариант 4), достаточно поменять одну строку в одном файле.

## 6. Объяснение ошибки из п. 8 методички

**Фрагмент:**
```java
double total = price * quantity - discount;
```

**Ошибка:** `discount` трактуется как **абсолютная сумма в рублях**, тогда как по заданию скидка задаётся **в процентах от 0 до 30**. Кроме того, в этой формуле **не учитывается НДС**, который по правилам должен вычисляться **после применения скидки**.

**Пример, где это видно:**
- `quantity = 10`, `price = 1000`, `discount = 10` (то есть 10 %).
- По ошибочной формуле: `10 × 1000 − 10 = 9990` ₽.
- По правильной: `10 × 1000 × (1 − 10/100) × (1 + 40/100) = 10000 × 0.9 × 1.4 = 12600` ₽.

Разница — 2610 ₽. Ошибка не падает, а **тихо даёт неверный ответ** — самое опасное.

**Правильный подход в моём проекте:**
```java
double base  = OrderCalculator.calculateBase(quantity, price);
double after = OrderCalculator.applyDiscount(base, discount);    // discount в %
double total = OrderCalculator.calculateVat(after, OrderCalculator.VAT_RATE);
```

## 7. Обоснование выбора типов `int` и `double` и ограничение `double`

**`int quantity`.** Количество единиц — всегда целое, диапазон `1…10 000`. `int` (32 бита, до 2.1 млрд) с запасом вмещает эти значения и **не допускает** дробного количества на уровне типа.

**`double price`, `discount`, `VAT_RATE`.** Денежные и процентные величины могут быть дробными (2490.50 ₽, 5 %, 40 %). `double` даёт 15–16 значащих цифр, чего достаточно для 5 000 000.00 ₽.

**Ограничение `double` для денежных расчётов.** `double` — двоичная плавающая точка; не все десятичные дроби представимы точно (`0.1 + 0.2 ≠ 0.3`). Для одной операции погрешность ~1e-15, но при накоплении (много позиций в заказе, повторное округление) она может «вылезти» в копейку. В реальных системах для денег используют `BigDecimal` или `long` (копейки). В учебной работе `double` допустим, но вывод делается через `%.2f`, что **явно** округляет результат.
