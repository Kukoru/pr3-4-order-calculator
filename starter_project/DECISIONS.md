# DECISIONS

Принципиальные решения, принятые при выполнении практической работы №3–4.

**Вариант 7.** Изменяемый аспект — ставка НДС. Значение: **40 %**.

---

## Решение 1. Единая точка расчёта — `OrderCalculator.calculateTotal`

### Что сделано
Все арифметические формулы (база → скидка → НДС) собраны в один метод
`OrderCalculator.calculateTotal(int, double, double, double)`.
В `Main.run` не осталось ни одной арифметической операции — только
вызов `validate(...)` и `calculateTotal(...)`.

### Почему так
1. Устраняет дублирование формулы в нескольких местах.
2. Исключает ошибку из п.8 задания:
   ```java
   double total = price * quantity - discount; // discount как рубли — неверно
   ```
   где `discount` ошибочно трактуется как абсолютная сумма в рублях,
   а не как процент, и не учитывается НДС.
3. Порядок «сначала скидка, потом НДС» задан ровно в одном месте —
   его невозможно случайно перепутать.

### Где в коде
- `OrderCalculator.calculateTotal` — точка входа.
- `OrderCalculator.calculateBase`, `applyDiscount`, `calculateVat` —
  вспомогательные шаги, каждый со своей ответственностью.
- `Main.run` вызывает только `calculateTotal`.

### Отвергнутая альтернатива
Писать формулу прямо в `main`:
```java
double total = qty * price * (1 - disc / 100) * (1 + VAT_RATE / 100);
```
Отвергнуто: формула размазана по UI-коду, её нельзя переиспользовать
в `SelfCheck`, при смене правила придётся править `main`.

## Решение 2. Проверки вынесены в `validateQuantity` / `validatePrice` / `validateDiscount`

### Что сделано
Каждая граница оформлена отдельным методом, который возвращает
`String` — текст ошибки, или `null`, если значение корректно.
Общий метод `validate(...)` вызывает их по очереди и возвращает
первую найденную ошибку.

### Почему так
1. В `Main` выводится **конкретная причина**, а не общее
   «значения вне диапазона» — это требование п.3 методички
   («программа должна вывести понятное сообщение»).
2. Границы заданы константами `MIN_QUANTITY`, `MAX_QUANTITY`,
   `MIN_PRICE`, `MAX_PRICE`, `MIN_DISCOUNT`, `MAX_DISCOUNT` —
   при изменении требования правится одно место.
3. Легко тестировать: `SelfCheck` проверяет каждую границу
   отдельным вызовом `isValid(...)`.

### Где в коде
- Константы — в начале `OrderCalculator`.
- Методы `validateQuantity`, `validatePrice`, `validateDiscount`,
  `validate`, `isValid` — там же.
- `Main.run` использует `validate` и печатает текст ошибки.

### Отвергнутая альтернатива
Один большой `if` с общим сообщением:
```java
if (qty < 1 || qty > 10000 || price <= 0 || price > 5_000_000
        || disc < 0 || disc > 30) {
    System.err.println("Ошибка ввода");
    return;
}
```
Отвергнуто: пользователь не понимает, **что именно** он ввёл не так;
границы размазаны по условию без именованных констант.

## Решение 3 (вариант 7). Ставка НДС — константа `VAT_RATE = 40.0`

### Что сделано
Ставка НДС вынесена в `public static final double VAT_RATE = 40.0`
в классе `OrderCalculator`.

### Почему так
По варианту 7 требуется ставка НДС 40 %. Это бизнес-правило,
которое должно жить в одном месте. `Main` и `SelfCheck` не знают
конкретного числа — они получают его через `OrderCalculator.VAT_RATE`.

### Где в коде
`OrderCalculator.VAT_RATE`.

### Что даёт при смене требования
Если завтра ставка станет 25 % (вариант 4) или 10 % (вариант 1) —
достаточно поменять **одну строку** в `OrderCalculator`,
не трогая ни `Main`, ни `SelfCheck`, ни диаграммы.

### Отвергнутая альтернатива
Захардкодить `* 1.4` прямо в формулу. Отвергнуто: магическое число
невозможно найти поиском и легко забыть поменять в нескольких местах.

## Как эти решения связаны с диаграммами

- **Activity-диаграмма**, блок A2
  (`sum = base×(1−discount/100); total = sum×(1+VAT_RATE/100)`)
  — это буквально тело `calculateTotal`.
- **Диаграмма классов**, класс `OrderCalculator`
  — содержит константы `MIN_*`/`MAX_*`/`VAT_RATE` и все методы,
  упомянутые выше. Соответствует коду один-в-один.
